# Agent Note: Canonical packed manifests make release tarballs reproducible

Status: implemented

English | [中文](2026-08-15-deterministic-packed-manifests.zh.md)

## Problem

`pnpm pack` resolves workspace dependency ranges before publication, but the exported `package.json` dependency maps do not have stable key order. Two clean builds of the same package can therefore contain identical program files and semantically equal manifests while producing different tarball checksums. The Windows desktop runtime lock seals those checksums, so a lock generated from one clean build drifts during the next clean CI build.

## Decision

The release pack boundary canonicalizes every exported manifest and repacks the payload before validation. Object keys are sorted recursively, array order is retained, lifecycle scripts are disabled, and npm performs the final archive construction. An isolated cache prevents concurrent or host npm cache state from affecting the operation.

This applies to both the dsh and vendored release families because both use `scripts/release/pack.ts`. The Landlock entry retains its direct pack path but passes the resulting archive through the same normalizer. Its exported `optionalDependencies` map also undergoes workspace range conversion and therefore requires the same canonical boundary.

## Alternatives considered

**Ignore manifest ordering when building the desktop lock.** Rejected because the lock intentionally seals the exact publish artifacts proven by the preceding release job. Hashing a semantic projection would allow the published bytes and the locked input to differ.

**Commit a lock generated by the latest CI artifact.** Rejected because another clean pack can choose a different key order, creating a self-repeating lock update instead of reproducible inputs.

**Replace pnpm's workspace export with a repository-owned manifest transformer.** Rejected because pnpm remains responsible for workspace range conversion and publish-field handling. Canonicalization begins only after that maintained transformation has produced the publishable manifest.

## Consequences

- Tarball identity is reproducible for equal payloads even when pnpm emits dependency maps in a different order.
- Directly packed inputs to the dsh release proof must call `release:normalize-tarball` before the proof consumes their bytes.
- Release packing performs a second local archive pass and therefore takes longer.
- Package lifecycle scripts do not run during normalization; the first `pnpm pack` remains the owning build and payload-selection step.
- A package whose exported payload cannot survive extraction and scriptless npm repacking fails at the release boundary before publication.
